# Native Administrator terminal boundary and validation

The release has an explicitly opened Administrator PowerShell terminal backed by Windows ConPTY. It runs separately from the existing JA21 JavaScript XPU worker. `Invoke-JA21Terminal -Terminal 1 -Command 'xpu info'` and `-Terminal 2` send bounded command requests to the two existing XPU terminals; the function returns a result only after a matching completed reply. Unknown or cancelled outcomes raise an explicit error and are never automatically retried.

The non-elevated controller executable is fixed at `tools/JA21-Admin-Terminal.exe`. Only an `open` request launches its helper with the Windows `runas` verb and the ordinary UAC consent prompt. The helper requires an Administrator role and authenticates a random local named pipe against the launched helper PID and exact executable path. The helper likewise verifies its pipe server PID and image. Pipes have a protected current-user SID ACL; a fresh nonce and session token fence requests. Delegation verifies that its pipe client is the owned PowerShell process, rather than an arbitrary process that can print terminal text.

The native WebView2 bridge accepts only the exact sealed `https://ja21-silicon.invalid/index.html` document, after successful navigation, with a fresh document token. Reload/navigation closes the controller and rotates this token. A literal, matched `cancel-open` operation handles cancellation while UAC is pending. No .NET/COM host objects are exposed. Input, output, command/result, line/frame, request, and UI-queue sizes are bounded. The UI has one batched output drain, rather than one unbounded Dispatcher allocation per terminal chunk. Teardown has one interlocked owner, and the HPCON resize/close lifetime is synchronized. The owned PowerShell process tree belongs to a kill-on-close job.

Compilation and strict protocol fixtures passed against the final current sources. The measured token was not an Administrator token. Actual ConPTY startup, Unicode output, arithmetic entered through terminal input, and ResizePseudoConsole were observed. The delegation function was present and invoked. Its local named-pipe connection could not complete in this execution environment. Independent raw Win32 opening of the exact waiting pipe returned `ERROR_ACCESS_DENIED` (5); same-process C# threads and ordinary child processes also failed, as did different PowerShell constructor forms and default/user-only ACLs. This establishes a permission gate rather than a PowerShell constructor or ConPTY routing error. The controller checks local IPC before requesting UAC and reports this gate without opening an elevation prompt.

The UAC consent flow, elevated startup, and the complete native Administrator-to-XPU delegation path remain **NOT_RUN**. Compilation, ConPTY observations, and mock result fixtures do not close those gates. The native GUI/restart acceptance harness is a separate test and must be reported from its own current results.

Two actual startup issues were fixed. A ConPTY child inherited redirected parent standard handles; selecting `STARTF_USESTDHANDLES` with null standard handles directs it into the pseudoconsole. The PowerShell child also inherited a launcher-specific module path and stopped at a publisher prompt for that unrelated runtime's PSReadLine files. The child now uses ordinary Windows PowerShell module locations. Its execution policy, UAC, publisher trust and machine settings are unchanged. Its own PSReadLine session uses `SaveNothing`, so privileged command history is not written to the user profile. No publisher approval was automated.

The native console now uses standard WPF WebView2. Independent probes showed ordinary controllers and standard WPF WebView2 succeeding while composition-controller creation failed with HRESULT `0x8000FFFF`, before mapping/navigation. The console has no WPF overlay chrome; generic browsing retains its composition control. Both use the same WebView2 document engine and the existing origin, resource, permission, download, CSP and host-object policies.

An independent exact-byte profile comparison then isolated a path-dependent IndexedDB startup failure: a 176-character profile failed to open its backing store, while a fresh 121-character profile booted Online. The console now rejects profile paths longer than 150 characters before browser initialization, reserving the observed 75-character origin suffix and 32 characters for LevelDB child files. This is a conservative application storage budget. It leaves existing workspace contents in place and gives a clear path/length error; any migration requires an explicit choice and preserved backups. The acceptance executable uses a fresh short workspace under `D:\Codex\hermit-native-validation\qa\` with the existing explicit external-workspace test policy. Production storage remains under the package workspace. Its long `hpu bytes` report waits for an exact completion marker and following prompt, then verifies the actual operation/field preview; short file commands still require strict begin/end output captures. Any acceptance failure captures the first document state and screenshot before teardown.

Microsoft's primary documentation describes [ConPTY creation, streams, resize and teardown](https://learn.microsoft.com/en-us/windows/console/creating-a-pseudoconsole-session), [named-pipe client PID verification](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeclientprocessid), and [WebView2 WPF hosts](https://learn.microsoft.com/en-us/microsoft-edge/webview2/platforms/wpf). The redirected-stdio edge case and the null-standard-handle fix are documented by Microsoft's terminal maintainer in [discussion 15814](https://github.com/microsoft/terminal/discussions/15814).
